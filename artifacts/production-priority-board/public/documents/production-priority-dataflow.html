03

1. Source rowset and mandatory scope filters

The first CTE filters the machine view before any order, demand, team, KPI, or data-quality result is produced.

Required source predicate

production-priority-filters.ts → requiredProductionPriorityWhereSql() and isRequiredProductionPriorityRow()

Guardrail
Calculation / rule

Keep only itemnumber != '02002107' AND sc2 in [Electmech, Machine, Hydraulic] AND sc1 in the approved list AND sc3 in the approved list AND normalized status not in [COMPLETED, REPORTEDFINISHED] AND salesorderpoolid does not contain 'Consign' (case-insensitive).

Result in the app

The filtered machine CTE is the only rowset passed into stop auditing, linkage auditing, order mapping, demand derivation, and quality counts.

Approved SC1 values

production-priority-filters.ts → ALLOWED_SC1

Guardrail
Calculation / rule

Automated, FoldingEnd, HDT, Met-Impact, MFI, Plas-Impac, Retrofit, SL-Series, Torsion, Horizontal.

Result in the app

Rows outside the approved SC1 taxonomy never reach the browser.

Approved SC3 values

production-priority-filters.ts → ALLOWED_SC3; use-production-data.ts → useSC3Teams()

Guardrail
Calculation / rule

2000SL, SL-ST, Misc, IT406, HDVT3, 600SL, Torsion, 300SL, 1000SL, NO-CNSL, MP1500, MP1200MAN, MP1200MWLD, MP1200ETO, CNSL-HYD, IT542, 799, CNSL-NOHYD, HDVT6.

Result in the app

The selector can only be populated by approved SC3 values that have active returned orders; an approved team with no active rows is not shown.

Audit row identity

production-priority.ts → machine AS MATERIALIZED

Transform
Calculation / rule

ROW_NUMBER() OVER () AS audit_row_id, machine.*

Result in the app

Each base row can be joined back to the stop and linkage audit CTEs without relying on a possibly duplicated production-order number.

04

2. Linkage audits

The server performs the relational checks before it labels a work order linked, partial, or unlinked.

Sales header linkage

production-priority.ts → linkage_audit; salesorderheaderv3staging

Transform
Calculation / rule

Header matches when trimmed sales order, data-area/company, and non-empty machine item prerequisites are present; salesordernumber and dataareaid must match.

Result in the app

salesHeaderMatched is a boolean input to linkageStatus and data-quality counts.

Sales line linkage

production-priority.ts → linkage_audit; salesorderlinev2staging

Transform
Calculation / rule

Line matches the header on sales order + data area and the machine on itemnumber.

Result in the app

salesLineMatched verifies that the work-order item has a corresponding sales-order line.

Production demand linkage

production-priority.ts → linkage_audit; prodproductionorderheaderstaging

Transform
Calculation / rule

Production matches the line on inventory-lot demand id + sales order + data area + item number, and matches the machine production order number; inventorylotid must be non-empty.

Result in the app

productionDemandMatched verifies that the source work order is tied to the same sales-line demand.

Deterministic linkage status

production-priority-filters.ts → isValidatedProductionPriorityLinkage(), getProductionPriorityLinkageStatus()

Transform
Calculation / rule

If sales order is blank → Unlinked. Otherwise Linked only when sales order, company, item, inventory-lot demand id, header match, line match, and production-demand match are all true; otherwise Partial.

Result in the app

Each production order carries linkageStatus and linkageAudit booleans; Partial adds the LINKAGE NOT VALIDATED exception.

05

3. Server normalization and order derivation

Raw PostgreSQL values are normalized into the typed ProductionOrder shape before the response is validated.

Text normalization

production-priority.ts → text(); production-priority-filters.ts → text()

Transform
Calculation / rule

null/undefined → ''; all source strings are String(value).trim().

Result in the app

Whitespace does not create false links, empty labels, or inconsistent filters.

Usable dates

production-priority.ts → usableDate(), iso()

Transform
Calculation / rule

A date is usable only when it exists and getUTCFullYear() >= 2000; otherwise it becomes ''.

Result in the app

ERP year-1900 placeholders and nulls do not appear as real due dates or create false date exceptions.

Status normalization

production-priority.ts → normalizeStatus()

Transform
Calculation / rule

Uppercase source status; contains START → STARTED; contains RELEASE → RELEASED; otherwise ''.

Result in the app

By product decision, the API exposes exactly two operator statuses to the board.

Active production rows

production-priority.ts → activeRows

Guardrail
Calculation / rule

From required rows, keep rows with a non-empty productionordernumber and a normalized status of STARTED or RELEASED.

Result in the app

orders[] excludes Scheduled, Complete, blank, and any other status text, the same way it always excluded completed/reported-finished rows, along with rows without a production work order.

Route-derived build start/end dates

production-priority.ts → route_ops, build_dates CTEs

Transform
Calculation / rule

From vw_productionroutedetailsd365 joined on productionordernumber + dataareaid: buildStartDate = scheduledfromdate of the first operation (by operationnumber ascending) whose operationname is not 'Warehouse Pick%'; buildEndDate = scheduledenddate of the last operation (by operationnumber ascending) whose operationname is not 'Warehouse Receive%'; buildEndDate falls back to deliverydate when the order has no route rows.

Result in the app

Build Start Date and Build End Date reflect when in-house production work actually begins and finishes on the route, matching how the Shop Floor App treats warehouse pick/receive as staging steps rather than production work.

Build, ship, stage, and resource fields

production-priority.ts → activeRows.map()

Transform
Calculation / rule

salesShipDate = confirmedshippingdate || requestedshippingdate; currentStage = Task || Assy_Resource || Resource1; resource = MachineResource || Resource1 || Resource.

Result in the app

The queue gets one sales ship date alongside the route-derived build dates; order details retain concise stage/resource labels while rawResource retains the original Resource text.

Exception flags

production-priority.ts → exceptionFlags

Transform
Calculation / rule

Add HOLD when stage/resource contains Hold; BUILD & SHIP PAST DUE when both dates are past due; BUILD DATE PAST DUE or SHIP DATE PAST DUE for one; NO BUILD DATE when build date is blank; LINKAGE NOT VALIDATED or UNLINKED from linkage status.

Result in the app

The status and detail panel can explain late, hold-instruction, missing-date, and linkage conditions without recalculating them independently. By product decision, a stop condition no longer changes an order's status or excludes it from priority.

06

4. Future-demand derivation

Demand without a production work order is still calculated from the same filtered source rows, but by product decision it only feeds the data-quality count — the Board no longer displays a demand panel or KPI.

Future-demand candidate

production-priority.ts → hasFutureShipDate(), demand

Output
Calculation / rule

Keep required rows where productionordernumber is blank AND salesordernumber is non-empty AND confirmedshippingdate or requestedshippingdate is usable and >= today at midnight.

Result in the app

Each candidate becomes demand[] with status NO WORK ORDER and never enters orders[] or the executable priority sequence.

Demand display fields

production-priority.ts → demand.map()

Transform
Calculation / rule

requestedDate = ordercreationdatetime || requestedshippingdate; salesShipDate = confirmedshippingdate || requestedshippingdate; qty = Number(orderedsalesquantity) or null.

Result in the app

These fields remain on the API response for downstream/data-quality use, even though the Board no longer renders a demand panel.

Data-quality-only usage

production-priority.ts → dataQuality.futureDemand

Output
Calculation / rule

demand.length feeds dataQuality.futureDemand; the client does not filter, sort, or display individual demand rows.

Result in the app

Future demand without a work order is visible only as a single count in the collapsible Data quality panel, not as an interactive list.

07

5. Data-quality calculations and API response

The API counts the same normalized collections that it returns, so the data-quality panel is traceable to the live response.

Work-order shape

production-priority.ts → dataQuality

Output
Calculation / rule

machineRows = required filtered rows; validWorkOrders = orders whose workOrder matches /^\d{6}$/; duplicateWorkOrders = number of distinct work-order values with count > 1.

Result in the app

The panel shows source-row volume, valid six-digit work-order count, and duplicate work-order count.

Sales-order linkage counts

production-priority.ts → dataQuality; production-priority-filters.ts → isValidatedProductionPriorityLinkage()

Output
Calculation / rule

populatedSalesOrders and compatibility linkedOrders count non-empty salesOrder values; validatedSalesOrderLinks count all seven linkage prerequisites passing; partialLinkages count linkageStatus = Partial; unlinkedOrders count linkageStatus = Unlinked.

Result in the app

Operators can distinguish a populated sales-order number from a fully validated header/line/production-demand relationship.

Demand and validity counts

production-priority.ts → dataQuality

Output
Calculation / rule

futureDemand = demand.length; futureDemandAlreadyLinked is currently 0; invalidSC3 counts returned orders with blank SC3; invalidDates counts source rows with a non-null deliverydate that cannot be parsed.

Result in the app

The response exposes forward-demand and remaining shape/date indicators used by the Board and downloadable dataflow document.

Response validation and freshness

production-priority.ts → GetProductionPriorityResponse.parse(), getSnapshot()

Guardrail
Calculation / rule

Parse orders, demand, dataQuality, and dataAsOf with GetProductionPriorityResponse; cache a successful snapshot for 60,000 ms; dataAsOf = 'Azure PostgreSQL · ' + current ISO timestamp.

Result in the app

A malformed response fails explicitly, repeated reads reuse the short server cache, and the browser can label evidence with its source timestamp.

08

6. Browser calculations and operator views

The browser does not query the database. It transforms the validated API snapshot into the selected team’s queue and presentation state.

Team list, counts, and default

use-production-data.ts → useSC3Teams(), useSC3Counts(), useSessionSC3()

Transform
Calculation / rule

teams = unique non-empty order.SC3 values sorted alphabetically; team count = non-complete orders per SC3; default team = highest count, then alphabetical tie-breaker; selected team persists in sessionStorage.

Result in the app

SC3 controls the queue, KPIs, exceptions, and demand view without changing the server snapshot.

Queue filtering

use-production-data.ts → useProductionData()

Transform
Calculation / rule

Select a specific SC3 team or All; search lowercases and matches workOrder, salesOrder, or customer; then apply the Started/Released status filter or the Past Due filter.

Result in the app

The visible table is a selected, searchable operational view of the snapshot, with All providing a cross-team queue.

Queue sorting

use-production-data.ts → byDateThenWorkOrder(), useProductionData()

Transform
Calculation / rule

Work order/customer sorts lexically. Date sorts use the selected date ascending, with missing dates last and work-order tie-breaks. Default priority sort uses build end date, sales ship date, and work order.

Result in the app

The first row in the visible queue is the next executable work order.

Executable priority number

use-production-data.ts → getExecutablePriority()

Output
Calculation / rule

priority = index of the order in the visible, sorted queue + 1.

Result in the app

By product decision, every visible order receives a numeric priority; a stop condition no longer removes an order from the sequence.

KPI calculations

use-production-data.ts → useStats()

Output
Calculation / rule

Active work orders = total visible orders; Started/Released = visible orders with that status; Build date past due = visible orders whose buildEndDate is before today.

Result in the app

The header KPI strip reflects the current team, search, status filter, date filter, and sort view.

Live evidence state

use-production-data.ts → usePrioritySnapshot(); generated documents are static and do not present live evidence

Guardrail
Calculation / rule

Loading while the first query is pending; Live after a successful snapshot; Stale when a refresh fails after a prior snapshot; Unavailable when the first query fails with no snapshot.

Result in the app

The Dataflow and Requirements Review documents do not present empty fallback zeros as verified live evidence.

7. Deliberately not calculated

The following values are intentionally absent from the dataflow and API because the product scope is operational priority, not capacity planning.

Capacity and utilization

Product scope decision documented in the Requirements Review and replit.md

Guardrail
Calculation / rule

No available hours, labor hours, resource loading, utilization percentage, finite scheduling, bottleneck score, or capacity gap is calculated.

Result in the app

The board communicates sequence, lateness, and stops without making capacity claims.

Executable schedule

use-production-data.ts → getExecutablePriority()

Guardrail
Calculation / rule

Priority is an ordered view index, not a promised start time, finish time, machine allocation, or optimized schedule.

Result in the app

Supervisors use the order as a transparent decision aid; the app does not imply that an order is scheduled for a particular hour.
