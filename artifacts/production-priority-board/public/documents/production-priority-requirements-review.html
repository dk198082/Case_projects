Production Priority Board requirements review

A standalone record of how the current implementation maps to the production board requirements. Partial and data-dependent areas are called out instead of being treated as verified passes.

01

Source, scope & architecture

The board is an operational priority and visibility tool, not a scheduling or capacity-planning engine.

Live source and runtime boundary

Use the supplied production data while keeping the UI independent from the raw source format.

Fulfilled
Functional behavior

The board loads the current production snapshot and keeps the original workbook only as an audit/reference artifact.

Technical evidence

The browser reads the read-only production-priority API. The API adapter reads Azure PostgreSQL through d365fo.vw_salesprodmachines365 and normalizes the response.

Layered data architecture

Separate source data, linking/normalization, business rules, SC3 view, and presentation.

Fulfilled
Functional behavior

Operators see a concise queue without raw workbook parsing details.

Technical evidence

Azure normalization and stop/filter rules live in the API; SC3 filtering, sorting, KPIs, and display behavior live in reusable hooks and page components.

Capacity-planning boundary

Do not show resource loading, utilization, labor capacity, finite scheduling, available hours, or bottleneck calculations.

Intentionally out of scope
Functional behavior

The board answers what to work on next and what is late or blocked without pretending to optimize capacity.

Technical evidence

No capacity, labor, utilization, bottleneck, or resource-loading calculations are present in the live contract or UI.

02

Linkage, source fidelity & validation

Production and commercial context is carried from the source view, with visible data-quality indicators.

Production/order relationship visibility

Connect work orders to sales orders and retain the production, customer, and SC3 relationship.

Partial / data-dependent
Functional behavior

A work-order row shows production and commercial context from the live source and makes partial or unlinked exceptions explicit.

Technical evidence

The API reconciles source sales headers and item lines to production-order demand using sales order, company, item, and inventory-lot demand identifiers. This requirement becomes fulfilled only while that audit is live.

No invented source values

Blank source fields remain blank or display an em dash; customer information must come from linked source data.

Fulfilled
Functional behavior

Unavailable customer, date, destination, or reference details show as — instead of fabricated values.

Technical evidence

The adapter trims source text, treats invalid/placeholder dates as empty, and maps absent fields to empty strings that the UI renders safely.

Pre-render data-quality checks

Validate work-order shape, linkage, SC3 values, dates, duplicates, future demand, and stop detection before rendering.

Partial / data-dependent
Functional behavior

The expandable Data quality panel exposes the current validation counts without distracting production users.

Technical evidence

The API reports valid six-digit work orders, duplicate orders, populated sales-order numbers, fully validated links, partial/unlinked links, invalid SC3 values, invalid dates, and future demand.

03

SC3 team structure & navigation

SC3 is the primary operating context and controls the queue, KPIs, exceptions, and demand view.

Dynamic active-team selector

Organize the board around SC3 and show active-order counts for available teams.

Fulfilled
Functional behavior

Production users can select an SC3 team and immediately see its active-order count and queue.

Technical evidence

The client derives the selector and counts from the API’s current non-complete orders. The server applies the approved SC3 allow-list before returning data.

Default team and session memory

Open on the team with the largest active workload and remember the user’s selection during the browser session.

Fulfilled
Functional behavior

The busiest available SC3 is selected initially; returning users keep their team while the session remains active.

Technical evidence

useSessionSC3 ranks active team counts and stores the selected value in sessionStorage.

Required source filters

Exclude the configured item, disallowed SC1/SC2/SC3 values, completed statuses, and consignment pools.

Fulfilled
Functional behavior

Operators only see the approved production scope; these rules cannot be disabled from the UI.

Technical evidence

The same predicate is applied in the Azure SQL WHERE clause and again server-side before orders, demand, KPIs, and teams are produced.

04

Priority queue & dates

The primary view is a dense, traceable list driven by route-derived build need first.

Single priority list

Present one vertically ordered list, with the first executable item as the next production priority.

Fulfilled
Functional behavior

The selected team’s queue is shown as a table so several orders can be compared at once.

Technical evidence

The client calculates executable priority after SC3, search, status, past-due, and sort filters are applied.

Internal build date leads

Prioritize internal build need, then sales ship date, then work order.

Fulfilled
Functional behavior

Build start, build end, and ship dates are all visible; the build end date drives the default order.

Technical evidence

Build start/end dates are derived per work order from the production route (first non-warehouse-pick operation start, last non-warehouse-receive operation end). Default sorting uses build end date, sales ship date, and work-order tie-breakers.

Stopped-order status override removed

By product decision, a stop condition no longer changes an order's displayed status or removes it from executable priority.

Intentionally out of scope
Functional behavior

A Started or Released order that also carries a stop condition (sales processing stop, sales-order stop flag, or Hold instruction) now displays and sorts exactly like any other Started or Released order.

Technical evidence

The server no longer computes a stopped flag, stop reasons, or a STOPPED status overlay; the sales-processing-stop audit join was removed from the query, and the client no longer excludes any order from the executable priority sequence or shows an Order stopped KPI.

Date exceptions

Highlight build past due, ship past due, both past due, and missing build dates.

Fulfilled
Functional behavior

Red dates and exception badges make late work visible without filling the entire row red.

Technical evidence

Exception flags are derived from normalized source dates; year-1900 placeholders are treated as missing.

05

Status, stage & exceptions

ERP status and resource context are translated into operator-friendly labels without inventing new states.

Operator status normalization

By product decision, show only two operator statuses: STARTED and RELEASED.

Fulfilled
Functional behavior

Rows show only Started or Released; orders that are Scheduled, Complete, blank, or any other source status are excluded from the board entirely, the same way completed orders always were.

Technical evidence

The API keeps a row only when its normalized status is STARTED or RELEASED; every other source status value is filtered out of orders[] before the response is built.

Stage/resource presentation

Retain current stage/resource context for order details while keeping the main queue concise.

Fulfilled
Functional behavior

The main table stays readable while the order detail view retains current stage and the full Resource value.

Technical evidence

The adapter aliases mixed-case resource fields into stable API fields; OrderDetailsDialog exposes current stage and resource without adding them to the main table.

06

Demand, details, filters & search

Forward demand stays separate from actionable work, with concise rows and deeper detail on demand.

Upcoming demand without a work order

Show future machine demand separately and never assign it a production priority.

Intentionally out of scope
Functional behavior

By product decision, the Board no longer surfaces an Upcoming demand panel or a demand KPI; supervisors work the executable queue only.

Technical evidence

The API still derives demand from filtered rows with a sales order, future ship date, and no production order, but only to feed the futureDemand count in the data-quality panel — the client no longer renders or filters demand rows for display.

Production detail view

Open a right-side drawer with production/commercial details for a selected work order.

Fulfilled
Functional behavior

Clicking a work order opens a right-side detail drawer that preserves the queue context.

Technical evidence

OrderDetailsDialog uses an accessible sheet panel to expose source fields, dates, raw resource, and linkage while retaining a full-width mobile presentation.

Simple filters and search

Support All Active, Started, Released, Past Due, and search within the selected team.

Fulfilled
Functional behavior

Operators can change status/date views, sort the queue, search by WO/SO/customer/PO/item, or select All to view every SC3 team.

Technical evidence

useProductionData applies the team, status, date, and search filters before calculating priority; the UI exposes a small fixed filter set.

07

Presentation, responsiveness & operator success

The visual system emphasizes priority, dates, customer context, status, and exceptions on dark green surfaces.

Visual hierarchy and palette

Use the dark green/lime corporate palette with readable secondary text, amber warnings, and red serious exceptions.

Fulfilled
Functional behavior

Priority, work order, build date, customer, sales order, ship date, and status are visible in the main row; stage and exception context remains available in order details.

Technical evidence

The theme tokens use #00281D, #B7FF00, #C2D2BE, white, amber, and red across board surfaces and state treatments.

Desktop and mobile layout

Optimize for a 1920×1080 production screen while remaining usable on laptops and mobile widths.

Fulfilled
Functional behavior

The table is dense on desktop, scrolls horizontally when needed, and the team/KPI controls wrap for smaller screens.

Technical evidence

Responsive Tailwind layout, horizontal table overflow, compact row spacing, and mobile-safe stacking are implemented in Dashboard.

Five-second operator questions

A supervisor should quickly identify next work, late work, started/released work, customer, build date, ship date, and forward demand.

Partial / data-dependent
Functional behavior

The board covers these questions when the source has the relevant fields; the requirements document records data-dependent gaps rather than hiding them.

Technical evidence

Queue, KPIs, exceptions, details, and demand are present. Current live data can legitimately produce zero demand or omit teams whose only rows are complete.
